## Credibility

### Source / provenance

Kaggle's Provenance section has two boxes.

**Sources**

```
whereismytrain.in public live-status cache:
https://whereismytrain.in/cache/live_status?date=DD-MM-YYYY&train_no=NNNNN

Underlying operational data originates with Indian Railways / NTES. This
dataset is an independent third-party collection and is not affiliated with,
endorsed by, or supplied by either whereismytrain.in or Indian Railways.
```

**Collection methodology**

```
Collected with an open-source Python harvester (fetch_live_status.py) that
issues one HTTPS request per (train number, date) against the public
live_status cache above, walking backwards in time from the present for every
train number in the fleet.

Each JSON response is flattened into one row per scheduled stop and written to
that train's CSV. A refetch rewrites exactly the affected rows, so collection
is idempotent and cannot duplicate records. Which dates are queried comes from
each train's timetabled running days, which skips about a third of possible
requests without losing coverage.

No imputation, smoothing or modelling is applied. A blank cell means the source
returned nothing for that field. Stops that never filed a status update are
retained with reported = 0 rather than dropped, so users can see the difference
between "on time" and "never reported".

Known collection limits, all documented in the dataset description:
- Delay values are never negative; the source reports 0 for both on-time and
  early running.
- Passenger services stopped from roughly 2020-03-22 into late 2021, leaving a
  real gap of around 650 days for most trains.
- Roughly 3 stops in 23 never report, and it is systematically the same quiet
  stations.
- Certain (train, date) pairs return a reproducible HTTP 500 upstream and are
  absent.
```

## Applying it

The dataset is already published, so there are two routes.

**Web UI, no re-upload.** Title, subtitle, description, tags, cover image,
provenance and update frequency are all editable under Settings. File and column
descriptions are editable per file on the Data tab. That last part is the painful
one at 12,935 files, so use the API for those.

**Kaggle API.** Needs `pip install kaggle` and `~/.kaggle/kaggle.json`.

```sh
# 1. real numbers for every train file
python3 scan_dataset.py /Volumes/shit/trains --out stats.json

# 2. small version first, to read before committing to the big one
python3 kaggle/build_metadata.py --schema first --out kaggle/preview.json

# 3. the real thing
python3 kaggle/build_metadata.py --out kaggle/dataset-metadata.json
```

Before pushing, pull the live metadata and diff it, so you can see exactly what
is about to change:

```sh
kaggle datasets metadata -p /tmp/live yadavsaurabh5517/indian-railways-dataset
diff <(python3 -m json.tool /tmp/live/dataset-metadata.json) \
     <(python3 -m json.tool kaggle/dataset-metadata.json) | head -50
```

Then update metadata in place:

```sh
kaggle datasets metadata -p kaggle -u
```

`-u` updates metadata without creating a new version, which matters here: a
`kaggle datasets version` run against a folder holding only the JSON would
publish a version containing only that file. Do not use `datasets version`
unless you are re-uploading the data too.

## A defect in the published data

140 of the 12,935 CSVs have no header row; their first line is a data row.
`pd.read_csv` on one of those promotes that record to column names and drops it,
with no error and no warning. The names are in `headerless-files.txt`.

The dataset card documents the workaround and each affected file's description
carries a warning, so people who read either will not be caught out. That is
mitigation, not a fix.

Fixing it properly means prepending the header line to those 140 files and
publishing a new version. The column order in them is already correct, so the
repair is mechanical:

```sh
HDR='date,train_no,train_name,train_type,seq,station_code,halts_here,sch_arrival,sch_arrival_date,sch_departure,sch_departure_date,act_arrival,act_arrival_date,act_departure,act_departure_date,delay_arrival_min,delay_departure_min,platform,distance_km,lat,lng,departed,reported,reported_at'
while read f; do
    [ -f "$f" ] || continue
    head -1 "$f" | grep -q '^date,train_no' && continue   # already fixed
    printf '%s\n' "$HDR" | cat - "$f" > "$f.tmp" && mv "$f.tmp" "$f"
done < headerless-files.txt
```

Re-run `scan_dataset.py` afterwards, because the row counts change by 140 and
`build_metadata.py` reads those totals.
